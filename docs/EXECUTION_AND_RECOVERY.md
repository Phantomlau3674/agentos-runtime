# 执行、崩溃与恢复语义

## 状态机

节点状态：pending → ready → running → verifying → verified。异常分支为 failed、blocked、awaiting_approval、unknown_effect、cancelled；输入变化后为 invalidated，需要新的执行意图。

任务状态：queued、running、awaiting_approval、blocked、verifying、succeeded、failed、cancelling、cancelled。只有所需节点 verified 且任务级验收全部通过才可 succeeded。

任何状态变化同时写入事件，使用任务版本号做 compare-and-swap，拒绝失效 worker 的旧结果。取消完成不意味着撤回已经发生的效果。

## 执行顺序

1. 解析引用与资源；验证输入版本及策略。
2. 获得必要租约；确认有效审批、额度和取消状态。
3. 持久化 operation intent 与唯一幂等 key。
4. 派发给受信适配器，执行操作。
5. 收集操作回执与输出；验收实际成果。
6. 持久化结果、证据及节点状态，释放租约。

步骤 4 与 6 之间存在崩溃窗口，不能通过一句“数据库事务”消除。

## 崩溃矩阵

| 崩溃点 | 重启后可知 | 恢复动作 |
|---|---|---|
| intent 写入前 | 尚无派发承诺 | 重新做策略/版本校验后调度 |
| intent 已落盘、调用未证实 | 是否发生效果可能未知 | 查询适配器 operation 状态，不能直接当没做 |
| 文件已写 staging、索引未提交 | 存在临时产物 | 验证 hash/manifest 后收编或清理孤立 staging |
| mock 草稿已写、响应丢失 | 可能已有草稿 | 用幂等 key 查询本地测试服务并核验，不新建重复草稿 |
| 原生/远程效果已发生、无法查询 | 不可确定 | unknown_effect，停止相关下游，交人处理 |
| 结果已记录、任务汇总未完成 | 节点可验证 | 检查产物仍存在且 hash 一致，再做任务级验收 |

## 重试分类

纯计算和不可变快照读：可重试，但受次数、时限和资源预算约束。明确没有发生效果的瞬时失败：适配器提供证据后可重试。已发生幂等写：对账确认后复用。未知效果：禁止盲重试。输入与授权变化：不是“重试”，而是重新规划或重新授权。

重试使用有界退避；延迟/次数也要计入端到端耗时和成本。重试不能把 terminal failure 掩盖为正常延长任务。

## 局部失效

产物依赖记录输入内容、处理规则、适配器版本、验收器版本和输出摘要。任一因素变化都使相关结果失效。只重做传递依赖中的必要节点；没有可靠依赖图时宁可重算，不进行猜测性复用。

业务 API 和图形应用的状态通常不能完整缓存；必须声明哪些版本可验证。截图 hash 变化或不变都不能单独证明目标对象是否一致。

## 文件提交与并发

仅在同一文件系统的受控输出目录做 staging→原子 rename；跨卷需要复制、校验与单独提交标志，不假装原子。原始输入通过快照使用，不原地更改。

worker 租约带 fencing token。过期 worker 不能更新当前数据库状态；但适配器若无法阻止旧 worker 对外写入，任务仍不得自动重新派发并发写。这也是不能泛称 exactly-once 的原因。

## 回退与补偿

v0 “放弃修改”意味着不采纳新副本，而不是撤销外部世界。邮件、支付、上传等真实外部写不在首版范围；以后每个适配器都需自己的补偿或确认语义，不能有全局万能 rollback。

检查点记录任务状态；应用快照、文件版本、外部操作回执是不同东西。接口和产品文案要把它们区分开。
