## 1. 原始输入被重复读取

在独立临时目录只提取归档中的 Python 源码，以 `unittest.mock.patch.object` 包装 `Runtime._read_sources`，没有更改其逻辑。

运行合成任务：100 个 CSV，每个 10 行，种子 7。运行结果 `SUCCEEDED`。

观测到 `_read_sources` 对原始输入调用 7 次，每次读取 100 个文件、35,860 字节；共 700 次逻辑文件读取、251,020 字节。这里不是实际物理磁盘 I/O 测量；页缓存可能服务重复读取。一次插桩运行不能支持任何真实 Agent 加速倍数。

源码位置：`runtime.py:160–171` 定义输入读取和哈希；`runtime.py:195–197` 每次完整读取并检查；`runtime.py:228–231` 在阶段开始检查；`runtime.py:310` 验收再读。

设计含义：先明确输入一致性契约，再考虑固定快照、发布前版本检查和按依赖局部失效。不能仅删除检测来降低耗时。只读副本不等于外部源无法变化；开始与结束相同也不证明过程中从未变化。

## 2. 全局重复 ID 使按文件汇总不能直接并行

源码：`tabular.py:23` 在所有文件共享 `seen`；`:25` 按文件名排序；`:40–47` 第一条语法有效的 ID 即占位，即使该行其他字段无效。

最小复现：a.csv 和 b.csv 都有 `same_id`，金额分别 10.00 CNY 与 20.00 CNY。

原始整体汇总：10.00 CNY，1 个 DUPLICATE_ID。

分别对两个文件调用 aggregate 再直接相加：30.00 CNY，0 个 DUPLICATE_ID。这说明天真的按文件 Map/Reduce 会改变语义，不是加速成功。

建议：文件解码/字段解析可先独立计算并缓存，按原契约进行全局 ID 顺序裁决，再汇总。缓存键必须覆盖文件名/行顺序等影响含义的依赖。

## 3. 当前计划契约仅是固定四阶段

源码：`contracts.py:10–11` 四个操作；`:35` 限定恰好四个节点；`:43–49` 强制相邻阶段串行。

建议：先增加输入/输出类型、读写资源、副作用与恢复策略，再扩大为受限 DAG。未知效果必须保守处理，不能由模型自行声明为安全纯函数。

## 4. 恢复版本绑定比较粗

源码：`runtime.py:30–35` 将七份源文件的全部字节计算为 engine_fingerprint；`:132–133` 不同则拒绝恢复。

含义：这种保守做法适合当前安全原型，但连不改变语义的源文件变更也会让旧回执不可复用。

建议：为动作实现、依赖环境、校验器分别固定版本和内容摘要；历史任务继续运行原版执行器，新版适配器做显式兼容迁移。不能简单忽略 fingerprint 检查。

## 检查范围
